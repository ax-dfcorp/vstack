# Changelog — pi-claude-bridge (ax fork)

## Unreleased

### Claude gets Pi's tool guidance, the same text every other model gets

Pi renders each active tool's prompt snippet and guidelines into its system prompt (`<tools>`, `<rules>`); the bridge replaced that prompt with the Claude Code preset and never carried them over, so the Claude models missed every tool rule other models follow (rpiv-todo's progress-board rules, the browser credential rules, `wait_for`, `slack_post` approval, `generate_image`). The append now carries them as a `<pi_tool_guidance>` part after the skills, taken from the text Pi rendered: tool names in the list are the ones Claude calls, a tool not offered over MCP is left out with the rules that name it, and Pi's two response-style lines are left out. On this Mac's setup that is 18,933 characters (about 5.4k tokens): 80 tool snippets and 35 rules. It sits in the frozen system-prompt append, so it is cached with it; a change to the active tools reaches a running session as a diff of that part.

A part added after every other part of the append now travels alone as an `added` part instead of forcing the whole append: a running session receives the new tool guidance once, at its size, not its full AGENTS.md, memory, and skills text again. A part added between others, a removed part, or a reorder still sends the full text. The blank line before an appended part is no longer reported as a change to the part before it.

Tests: `tests/unit-tool-guidance.mjs`; `tests/unit-append-update.mjs` updated for the appended-part rule. Unit 617 pass (2 environment skips), typecheck clean. Live on Claude Code 2.1.323, 2026-11-13: `tests/int-smoke.sh` 3/3; `tests/int-cache.sh` PASS (99% hit, 4 reuse / 0 rebuild). A fresh Opus 5.5 session and a fresh Fable 5.2 session in Daseo, asked for nine proposals and then "1, 3번만 먼저 하자", each kept all nine on the todo list with #1 and #3 completed and the other seven on hold with a reason (10 todo calls each; before this, Opus made none); the guidance sits in the recorded `prompt_snapshot` (18,933 characters) and later requests read 97-99% from cache. A session recorded before the change received it on its next turn as a 23,299-character diff update (an AGENTS.md hunk plus the added part), reading 61,794 tokens from cache and writing 8,903, with no rebuild.

### Fixes to the cache levers after an independent review and live runs (2026-11-07)

- A cached summary or warm-up that ends without a successful result, or with thinking and no text, now fails and takes the isolated path. Before, a resumed summary that produced only thinking was accepted, and Pi would have compacted to an empty summary.
- A `<system_prompt_update>` diff now goes out only when the parts keep their names and order. An added, removed, or reordered part, a part name with an apostrophe, or a literal `</part>` sends the full text: a diff names parts but not positions, and instruction order is precedence.
- A delivered update is recognized only when it opens the user record (the bridge always puts it first). A versioned block quoted or pasted later in a message no longer counts as a delivery, so it cannot suppress a real update.
- A warm-up counts, and is reported to the router, only if it read at least half of the last request's context from cache. A cold or mismatched prefix is logged as `cache_keep_warm_failed`, so the router never holds a session on an account for a cache that is gone.
- A query starting while a warm-up is in flight aborts the warm-up first, so two resumed children of one session never overlap.
- A warm-up refused because a query was running retries every minute until 58 minutes after the last request. Before, it gave up for that idle stretch.
- A session model with a summary substitute (`summaryModelOverrides`, Fable to Opus) always keeps the substitute's isolated summary. The override exists to keep summaries off the Fable window, the scarcest meter (claude-fable-first policy); a cached summary would be written by Fable itself. Cached summaries therefore apply to sessions without a substitute (Opus and others).

Measured live with Pi in RPC mode, 2026-11-07:

- Opus 5.5 high: an AGENTS.md line added and then reverted reached the model as diff updates of 905 and 860 characters (cache write 492 and 396 tokens). The model applied both, including the reversal. The warm-up after 60 s idle read 51,610 and 73,186 tokens from cache and wrote 312 and 189, with 4 output tokens.
- Fable 5.1 medium: diff updates of 1,224 and 860 characters, both applied. The warm-up read 54,546, wrote 131, with 4 output tokens.
- Compaction: 446 of 512 Pi compactions in the 17 days before were split-turn, and 142 of 165 Claude ones ran mid tool loop. Both kinds keep the isolated path, so the cached summary covers only the minority of between-turn, whole-turn compactions.

### One idle warm-up keeps a large conversation's prompt cache

A conversation's prompt cache expires 60 minutes after its last request, and the next turn then writes the whole conversation again (1.25 per token on the subscription weekly limit, against 0.025 for a read). Now, 53 minutes after the last real request of the top-level conversation, if that request carried at least 100,000 tokens, no request of it is running, and the account router still routes its model to its account, the bridge sends one tiny request through a resumed, non-persisted copy of the conversation's Claude session with the last turn's exact settings (tools denied, one turn), which reads the conversation from cache and extends its lifetime by an hour. At most one per idle stretch; the timer never keeps the process alive, so a host that unloads idle sessions at 60 minutes is unaffected. The router's new optional `recordCacheWarm` lets pi-local's router treat a warmed session's cache as alive for another hour without counting the warm-up as user activity. Settings: `keepWarm.enabled` (default on), `keepWarm.afterMinutes` (53), `keepWarm.minContextTokens` (100000), `keepWarm.maxWarms` (1); each warm-up's usage is logged as `cache_keep_warm` in the diagnostics log. Pi core's own cache warmer cannot fire for bridge models (they declare no prompt-cache lifetime). Measured 2026-11-07 on Haiku 5.5 with `afterMinutes` 1 and the minimum lowered for the test: the warm-up read 5,437 tokens from cache and wrote 437 on a 5,766-token context, the transcript was unchanged, and the next real turn read 5,437 from cache; with the default minimum the same small session got no warm-up.

Tests: `tests/unit-keep-warm.mjs`.

### Compaction summaries read the warm prompt cache

A compaction summary used to be an isolated request that sent the whole serialized conversation as uncached input, which the subscription weekly limit weighs 40 times a cache read. When Pi compacts between turns and the conversation's last request is under 55 minutes old, the summary is now written by a resumed, non-persisted copy of the conversation's own Claude session with the last turn's exact options (model, effort, account, tool declarations, recorded system prompt), so the conversation is read from cache. The request carries Pi's summary instructions, previous summary, custom focus, and the boundary after which messages stay verbatim; tools are denied and limited to one model turn. A split-turn or overflow compaction, a live query, an out-of-sync session, or a cold cache keeps the isolated request, and so does any resumed attempt that calls a tool, hits the length limit, or fails. Measured 2026-11-07 on Haiku 5.5 with a 379k-token session: the summary request read 379,270 tokens from cache, wrote 556, and produced all six of Pi's summary headings; the transcript was unchanged by it; the next turn rebuilt from the compacted history as before. The isolated request for the same conversation wrote 370,913 tokens. A live run with the transcript moved away fell back to the isolated request and the compaction completed. `tests/int-compact-mid-tool-loop.mjs` (live query, isolated path) and `tests/int-session-compact.mjs` pass.

Tests: `tests/unit-cached-summary.mjs`.

### A changed AGENTS.md, memory index, or skill list is sent as the parts that changed

When the bridge's system-prompt append changes during a session, the next prompt carries a `<system_prompt_update>`. It always held the whole append: a median of 142k characters on Fable, and the HYM memory index alone changed 242 times in 16 days (569 Fable and 809 Opus deliveries, each staying in its conversation for every later request). The update now names only the parts that changed, against what the model last received: a unified diff of a changed `<project_instructions>`, memory, skills, or forwarded-context part, the whole part when its diff exceeds 40% of it, added parts in full, removed parts by name, and the full text when the update would exceed half of it. Measured 2026-11-07 on Haiku 5.5 with a 41,876-character append and one AGENTS.md line changed between two turns: the update was 1,024 characters instead of 41,876 and that turn wrote 478 tokens to the cache instead of 26,199; both models quoted the changed rule correctly.

What the model last received is now read from the Claude transcript itself (the recorded snapshot, superseded by the last update after it; each update carries a `version` hash, and the text behind a diff is kept in `<piUserDir>/claude-bridge-append-versions/`). Two defects of the digest bookkeeping go with it: a change reverted to the original text (A → B → A) was suppressed although the model held B, and the delivered digest was saved with the Pi session but never restored, so every restart re-sent the full text. An unresolvable version falls back to a full update.

Tests: `tests/unit-append-update.mjs`.

### AGENTS.md reaches Claude once, not twice

Claude Code 2.1.277+ reads AGENTS.md on its own (built-in plugin `cc-plugin-agents-md@builtin`) and attached it to every new conversation's first message, while the bridge already forwards the same chain in the system prompt. Each Claude session therefore paid for its AGENTS.md twice on every request. The bridge now passes the plugin's documented option `instructionFiles: "claude-md"` through the `--settings` channel whenever it forwards the chain itself, so the CLI only reads CLAUDE.md. Measured 2026-11-07 on Claude Code 2.1.318: a new session in `ws/hym/apps/visual` sent 53,558 tokens on its first request instead of 94,501 (the attachment held 110,528 characters of AGENTS.md text), with all four AGENTS files still in the recorded system prompt. Sessions whose transcript already carries native instruction files keep the CLI loader until their next full rebuild: turning it off mid-session makes the CLI tell the model "Instructions no longer present", and Haiku 5.5 then answered that it had no project instructions although they were still in its system prompt. With that guard an existing session resumed on the new build read 12,268 of 12,270 tokens from cache and saw no notice. The comment that called an omitted `settingSources` isolation is corrected: the SDK then passes nothing and the CLI loads its default sources.

Tests: `tests/unit-native-instructions.mjs`.

### Every trailing user message is the prompt, not only the last one

Pi appends each steer that arrives in the same tool boundary as its own user message, so a context can end with two or more user messages. The bridge sent only the last one to Claude; the earlier ones were imported into the session file as history and never answered. Observed 2026-10-13: two Daseo `notifyOnFinish` notices for research workers landed 85 ms apart, the parent saw only the second, and the first worker looked unfinished until the user asked. `extractUserPrompt` and `extractUserPromptBlocks` now take the whole trailing run of user messages, joined with a blank line (images from every message kept, in order), and the session sync drops that many trailing messages instead of a fixed one. The live-steer path uses the same extractor, so two steers pushed into an active query arrive together too.

Tests: `tests/unit-user-prompt.mjs`.

### A model substitution restarts the live query at the next tool round

When Claude Code answers with a different model than the session requested (its refusal fallback, for example Opus 5 for Opus 5.5), the bridge now restarts at the next Pi callback instead of waiting for the next prompt. It stops delivering tool results into that query, discards it, and re-runs the turn on a fresh Claude session: a `model-substitution` rebuild with a new session id, never a resume of the swapped one. Before, the 2026-09-27 fix only restarted on the next prompt, and steers and follow-ups kept one query live for hours. One Opus 5.5 session ran 652 turns on Opus 5 on 2026-09-29, with no restart. The discard reuses the compaction-restart path, including its settlement wait and the continuation from the tool-result tail. A steer handed over with the tool results becomes the re-run's prompt. The substituted turn already shown stays in Pi history under the requested model id. If the fresh session is substituted again, the bridge stops after two consecutive restarts and delivers normally. It then warns once that the session continues on the substitute until the agent restarts or the model is switched. A turn answered by the requested model resets that count, which is kept per Pi session. The substitution warning now appears once per streak instead of once per tool round. The first query of a fresh Pi session, which has no shared session to mark, now also leaves its session due for a rotated rebuild, so the next prompt no longer resumes the swapped session. Diagnostics: `model_substitution_restart` and `model_substitution_restart_capped` in the diag log, and a new drain cause `model-substitution-restart`.

Tests: `tests/unit-model-substitution-restart.mjs`.

### Two parallel calls of the same tool pair with their own results

A message with two calls of the same tool (two `mcpScript` or two `read` calls) could lose both results: the bridge could not tell which MCP handler belonged to which call, returned `no matching tool_call id` to the model, and dropped Pi's real results as stale (20 such tool results in 30 days, 16 in turns with two calls of one tool; live repro 2026-09-29 01:17Z). The records and the handler's input now compare through the same tool schema the SDK validates with, so an undeclared key the model added (`timeout` on mcpScript) no longer makes the two differ. A handler that runs before its call's arguments are final waits for them instead of guessing between same-name calls. A lone call of its tool still pairs as before.

Tests: `tests/unit-same-tool-parallel-claims.mjs`.

### AGENTS.md forwarding matches Pi: global file plus every ancestor

The bridge now forwards the same context files Pi loads for its own system prompt: `<piUserDir>/AGENTS.md` first, then every `AGENTS.md` (or Pi's other candidate names) from the filesystem root down to the working directory, deduped by realpath, each in its own `<project_instructions path="...">` block under `# CLAUDE.md`. Before, only the nearest file was forwarded, so a Claude session inside a repository with its own AGENTS.md never received the rules in `~/AGENTS.md` or the global file, although GPT sessions on Pi did (found 2026-09-24). Live sessions receive the longer append once, as a `<system_prompt_update>` on their next turn. Isolated mode still forwards nothing.

Tests: `tests/unit-agents-md.mjs`; `tests/unit-isolation.mjs` updated for the new resolver.

### A compaction mid tool loop restarts the live query on the compacted history

When Pi's threshold auto-compaction fires inside a tool loop, the bridge no longer delivers that turn's tool results into the live Claude Code query. That query was still on the pre-compaction transcript, so the model kept seeing the full history. Pi's threshold check then fired again after every tool round, and each repeat was another full, uncached summary call: three in a row at 917k → 930k → 941k tokens in one session on 2026-09-23, with the Claude session id and `lastSync` frozen throughout. Now the provider detaches the live query from Pi's stream, closes it, and waits for it to settle. Teardown drains its waiting MCP handlers with the new `compaction-restart` cause, and the provider re-runs the same call. That re-run takes the REBUILD path (`rebuildReason=session_compact`, fresh session id) from Pi's compacted context, which already holds the summary, the kept tail, and the tool results. It continues from the tool-result tail the same way a turn-boundary compaction does. The only visible difference is that the turn no longer re-compacts. Session-tree rewrites during a live query take the same path. The same applies to the first query of a fresh Pi session, which has no shared session until it completes (a long single-prompt agent spends its whole task in it). The rewrite is recorded on that live query, and teardown turns the child's session id into a shared session due for the compaction rebuild. If that id was never captured, the re-run takes the ordinary first-turn rebuild instead. Genuine aborts, ordinary tool-result delivery, steering, and the one-shot summary lane are unchanged. Nested (subagent) query contexts keep the previous behaviour. Diagnostics: `compaction_active_query_restart` in the diag log, and the rebuild `syncResult` debug line now names its `reason`.

Tests: `tests/unit-compaction-restart.mjs`; `tests/int-compact-mid-tool-loop.mjs` now also asserts that the first post-compaction context is below the threshold, that a `session_compact` rebuild happened with a new session id, and that the tool output survived.

### Compaction and branch summaries run as isolated one-shot queries

Pi's compaction and branch-summary requests (`cacheRetention: "none"`) no longer go through the conversation's Claude Code session. Each one runs as its own short-lived query that has Pi's summarization system prompt as-is, no tools or MCP servers, no `resume`, and no persisted child session. It never touches the live query or the shared session cursor. Before this change, an auto-compaction that fired in the middle of a tool loop was written into the waiting query as a steer: the child waited for a tool result and Pi waited for the summary, so the turn hung until the stream-idle timeout (2 of 133 measured compactions). Now the turn continues. Between-turn `/compact` also stops re-reading the whole session transcript: it sends only the summary prompt, and the summary exchange no longer ends up in the main session history. Ordinary turns are unchanged (same resume, prompt cache, tools, and AGENTS.md forwarding). The first ordinary turn after a compaction still rebuilds the Claude session from the compacted Pi history.

Known limitation (resolved by the entry above): when compaction happened mid tool loop, the rest of that turn still finished in the pre-compaction Claude session.

Tests: `tests/unit-one-shot-summary.mjs` and `tests/int-compact-mid-tool-loop.mjs` (live).
